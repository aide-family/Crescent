# fix-v4：工作风格旁新增执行模式

状态：已实施，验证记录见 `docs/EXECUTION_PLANS.md`  
日期：2026-09-28

## 目标与方案选择

保留现有“工作风格”选择器及其四种风格，在它旁边新增独立的**执行模式**选择器。执行模式包含即时执行和计划执行：让只读查询保持顺畅，并允许用户核验一份具体的线上变更计划后，由 Agent 自动执行已批准步骤。两者是同一个执行模式控件里的选项：

1. **即时执行（现有标准行为）**：不要求先提交计划。已确认只读的命令自动执行；会改变状态、混合或不确定的命令仍逐条请求人工审批。
2. **计划执行（新增）**：Agent 可先做必要的只读调查并形成结构化变更计划。用户核验并批准该计划后，Agent 按原计划自动执行备份、变更和验证步骤；遇到错误、状态漂移或计划外需求立即停止。

不另加第三个独立的“无计划只读自动审批”模式：即时执行本身就是无计划路径，且现有逻辑已经自动放行静态只读及低风险命令。重复增加一个只改变名称、不带来明确行为增量的模式会让选择器更难理解。若基线调查发现目标只读查询仍频繁误入审批，应修复分类覆盖而不是重复加一个模式。

计划执行不是永久授权或全自动模式。每次任务仍须人工批准一份绑定目标、范围、命令和保护步骤的具体计划；切换到该模式本身不批准任何线上操作。

## 实施前基线与设计约束

- `src/shared/agent-style.ts` 中的极速、简洁、协作、详解只控制沟通密度。执行模式应与 `AgentStyle` 分离，不改变现有提示词、思考显示默认值或工作风格语义。
- `src/main/agent/command-classify.ts` 负责 Bash 命令风险分类：静态高风险规则优先；已知只读及低风险审计命令可自动通过；不确定或高风险命令进入审批流程。
- `src/main/agent/pi-terminal-bash.ts` 在命令进入终端前执行分类；`src/main/agent/command-approval.ts` 当前承载逐命令审批。计划审批需要在此基础上建立范围更明确的计划级授权，不能靠系统提示词或 Renderer 状态代替 Main 执行边界。
- `src/shared/agent-types.ts` 已有 `plan` 运行事件，但事件展示本身不构成结构化、可批准、可约束执行的变更计划。
- `docs/SECURITY_MODEL.md` 要求通过命令审核和审批保护状态变更；Electron 的 Main / preload / Renderer 边界及 `.cursor/rules/` 必须继续遵守。
- `src/shared/command-guard.ts` 会拆解 SSH、`kubectl exec`、`docker exec` 和受限 sudo 包装，按内部命令及本地选项分类；已知只读远程查询可自动执行，交互式 SSH、端口转发、ProxyCommand/LocalCommand、未知命令和敏感/间接 sudo 查询仍需审批。对应边界已有本地测试，验证记录见 `docs/EXECUTION_PLANS.md`。
- 即时执行已经自动放行静态只读命令。本计划不再把“新增只读自动审批”作为独立功能；后续改动应针对分类覆盖或运行验证中发现的具体缺口。

## 模式一：即时执行

- 这是现有标准审批行为的清晰名称，默认启用，不要求 Agent 为简单查询先生成计划。
- 只有命令被规则确定为只读、且审计结果允许自动通过时才自动执行；命令显示在可见终端并保留审核/执行记录。
- 用户的查询措辞不能单独授权命令。写入、修改、读写混合、含义不明或无法证明只读的操作仍逐条审批。
- SSH 是连接方式，不单独构成审批理由。若远端命令完整可解析且确认只读（包括明确目标上的只读 `kubectl`、`systemctl` 等命令），应像本机只读查询一样自动执行。分类器需审核解包后的远端命令及整条命令中的其他操作。
- 可解析的 `sudo <readonly-command>` 不应仅因出现 `sudo` 就被认作状态变更；需独立评估提权影响，并只在目标明确、内部命令被规则确认为只读、没有 shell/脚本逃逸且敏感信息控制有效时自动执行。`sudo` 不能成为跳过风险判定的通配白名单。
- 没有远端命令的交互式 SSH、端口转发、含 `ProxyCommand` / `LocalCommand` 等本地副作用选项、无法解包的 shell 脚本或未知远端命令均不能按只读查询自动放行。
- 查询任务中若 Agent 提出状态变更，应先请求现有命令审批；用户可拒绝后让 Agent 改用只读方案。

## 模式二：计划执行

### 计划与审批

1. Agent 先通过现有受限能力做只读调查，确认主机/集群身份、资源范围、现状、前置条件与潜在影响。此阶段不得执行变更。
2. Agent 提交结构化计划。计划至少包括：
   - 目标和范围：连接/目标主机、集群、命名空间、资源标识，以及明确排除的范围；
   - 只读预检：当前状态、适用条件和判定结果；
   - 备份/快照：要保护的数据或配置、创建方式、保存位置、保留期、敏感性，以及如何验证备份可用；
   - 精确变更步骤：命令、参数、执行目标和顺序；
   - 成功标准：每一步的预期结果及只读验证命令；
   - 停止条件、部分执行影响和恢复步骤，包括恢复步骤的风险与限制。
3. 用户检查计划并批准后，授权仅绑定这次运行中的计划内容、目标和范围。审批卡应清楚展示所有会改变状态的步骤，不能以摘要代替实际命令/参数。
4. 若目标、命令、参数、备份位置、顺序、前置条件或影响范围发生变化，原授权立即失效；Agent 必须停止并提交新计划让用户重新审批。

### 备份与变更执行

- 对可备份的数据、配置或资源，计划必须先创建备份/快照，并验证产物存在、可读且与目标对应，然后才执行依赖该备份的变更。
- 备份也是有副作用的操作，应作为计划步骤与变更一起展示并纳入计划审批；不能隐式先执行备份，也不能只在变更命令文本中拼入隐藏的复制操作。
- 备份可能含凭据或敏感数据。计划必须说明权限、保存位置和清理策略；备份结果不得写入日志或对话中的敏感内容。
- 若某类操作没有合理的备份方案，计划要提供适用的替代保护（例如可核对的变更前快照、回退步骤或服务冗余切换）；说明不可恢复的影响。保护措施不足以支撑安全执行时，不得因用户批准了模式而绕过风险门槛。
- 计划批准后按序执行已批准步骤。每步都记录开始、结束、结果及目标；备份未通过验证时禁止继续变更。
- 计划获批后无需对计划内每条命令重复弹审批；Main 进程仍须校验计划授权、目标绑定、步骤顺序和有效期。只执行被批准的步骤，不允许 Agent 临场生成替代命令。

### 停止、失败与恢复

- 命令非零退出、超时、连接或目标身份变化、前置条件不满足、备份验证失败、输出与成功标准不符，或 Agent 认为必须追加计划外操作时，立即停止后续变更。
- 停止后保留证据并报告已完成/未完成步骤、当前状态和风险；不得原样重试失败的变更，也不得自动扩大范围排错。
- 自动回滚不能作为通用默认。只有恢复动作本身已经在计划中清楚列出、明确触发条件、验证方式和风险，并且用户在计划审批时一并批准，才可自动执行；否则暂停并等待人工决定。
- 对不可逆、高影响或缺少可信恢复路径的操作，即使计划已批准，也可要求额外确认或拒绝自动执行；是否适用由明确风险规则决定，不交给模型自行豁免。

## 界面与状态

- 保留输入区现有“工作风格”选择器、四种选项及设置不变。在其旁边新增独立的“执行模式”选择器，提供“即时执行”和“计划执行”；不要将执行模式合并到工作风格菜单，也不要把两者混作 `AgentStyle`。
- 即时执行的描述：“只读命令自动执行；修改命令逐条确认。”计划执行的描述：“先核验并批准计划，再自动执行计划内变更；计划外操作会暂停。”
- 设置默认保持即时执行。计划执行应按单次任务/会话显式启用；每次具体变更都需要单独批准计划，不能因为上次批准或会话仍开着而复用授权。
- 执行模式状态与沟通风格分开定义、校验和持久化。旧配置缺少字段时安全回退到即时执行；恢复旧会话不得恢复未完成或已过期的计划批准。
- 中英文文案、键盘选择、当前选中状态和适当的风险提示必须齐全。菜单说明应明确“选中计划执行 ≠ 已批准计划”。

## 原实施计划

以下记录最初确定的实现步骤；完成情况和验证证据以本文件“实施中修正的安全边界”及 `docs/EXECUTION_PLANS.md` 为准。

### 1. 建立基线和风险目录

- 检查 `src/shared/command-guard.ts`、`src/main/agent/command-classify.ts`、`command-auditor.ts`、`pi-terminal-bash.ts`、`command-approval.ts` 及现有只读批处理路径。
- 整理只读、写入、混合、未知、Shell 包装、SSH、只读/写入 sudo、`kubectl exec`、`docker exec` 等命令的现有结果和审批行为；以此确认即时执行模式的现状及真实待解决问题。
- 为支持的变更类别列出备份能力、验证方式、恢复方式和不能自动恢复的情况；不对没有可靠保护办法的操作承诺全自动执行。

### 2. 设计结构化计划与授权模型

- 在共享类型中定义执行模式、变更计划、计划步骤、前置条件、备份产物、成功标准、失败状态和审批绑定信息。
- 授权至少绑定 run/session、目标连接或主机身份、计划版本/步骤摘要、有效期；一次性使用，运行结束或会话关闭后失效。
- 在 Main 进程验证所有关键字段并保有最终执行决策；Renderer 负责计划预览与用户审批交互，preload 仅暴露白名单 IPC。
- 重新评估当前 Pi `plan` 事件的用途。可以复用它呈现阶段进度，但审批与执行必须使用有类型约束的主机计划数据，不依赖自由文本解析。

### 3. 实现计划生命周期与执行器

- 实现“只读调查 → 提交计划 → 用户审批/拒绝 → 计划内步骤执行 → 验证/完成或中止”的主机控制流程。
- 计划执行应复用终端现有目标、命令审计、取消和日志机制；新增计划级授权只允许批准步骤按序通过，不移除静态危险规则、目标校验或执行超时。
- 对变更前备份进行独立执行与校验；备份不可用、计划过期或目标漂移时终止本次计划。
- 计划外命令、新错误恢复策略和自动重试一律暂停并请求新的用户决策/计划审批。
- 不引入 Electron EGG，不把 host 级安全能力移入 Pi 扩展或 Renderer。

### 4. 接入执行模式与审计视图

- 保留工作风格控件原样，在旁边新增执行模式控件；明确呈现即时执行与计划执行的不同授权流程和默认状态。
- 新增计划预览/审批 UI，能查看完整步骤、目标、备份和恢复信息；审批和拒绝可填写备注。
- 时间线与可见终端显示每一步状态、备份结果、停止原因和最终验证，不泄漏备份内容或敏感输出。
- 检查 App 重启、切换会话、关闭 Tab、SSH 断开、审批卡失效等生命周期；任何中断均不得留下可复用的计划授权。

### 5. 本地验证

- 按项目要求新增本地测试文件（`*.test.ts` / `*.test.tsx` 不提交），覆盖策略解析、计划审批绑定、步骤校验、备份验证、停止与恢复状态。
- 安全场景至少验证：只读预检自动运行；用户拒绝计划；审批后精确计划执行；目标/命令/参数改变使授权失效；备份失败阻断变更；变更非零退出立即停止；成功验证后结束；计划外命令暂停；连接身份变化中断；Tab 关闭取消未执行步骤；批准的回滚按触发条件运行；未批准回滚等待人工决定。
- 覆盖即时执行模式中本机及 SSH 只读自动通过、已解析只读 sudo 的策略、交互式 SSH/端口转发/未知远端命令不自动放行、写入逐条审批、混合与未知命令继续审批，以及旧配置兼容。
- 在运行中的 Electron 应用验证计划查看/批准/拒绝、执行进度、备份状态、错误中断和重新审批体验；确认原有四种沟通风格不变。
- 实现完成后运行 `npm run ci`；本地测试文件存在时同时运行 `npm run test:local`。实施阶段必须完成以上验证；本地测试文件保持不提交。

## 验收标准

- 用户能清楚区分工作风格与执行模式，并理解选择计划执行不会自动授权变更。
- 即时执行保持现有行为：明确只读命令自动执行；变更、混合和不确定命令逐条人工审批。
- 只读 SSH 远程命令不因 SSH 传输层而额外要求审批；审核器依据完整可解析的远端命令判断。sudo 只读命令经过单独的提权和敏感数据规则后，可按只读策略处理；SSH 交互会话、端口转发、本地副作用选项和未知命令仍受保护。
- 计划执行在任何变更前展示具体目标、命令、备份/替代保护、验证和恢复方案；每个计划都需独立批准。
- 用户批准后 Agent 只执行精确批准且绑定目标的步骤；备份失败、目标漂移、错误、超时、验证失败或计划外需求会停止后续变更。
- 计划中的恢复步骤只有经明确审批才可自动执行；授权不跨任务复用，计划变更会要求重新审批。
- 终端命令、计划步骤和执行状态保持可见；日志和 UI 不泄漏备份中的秘密。
- 旧配置与会话安全兼容，默认仍为即时执行，原四种沟通风格不回归。
- 设置区和输入区的工作风格四选项保持原样，执行模式作为其旁边的独立选择器工作。

## 范围外

- 不提供不经具体计划审批的线上全自动变更模式。
- 不自动批准 MCP、外部 API、Pi 写文件工具或未纳入计划执行器的副作用能力。
- 不允许自由形式模型输出、用户查询措辞或模式提示覆盖 Main 进程的风险分类和计划约束。
- 不支持的变更类别继续使用即时执行逐条审批；不把自由脚本包装成计划自动授权。

## 实施中修正的安全边界（2026-09-28）

1. 即时执行只让静态规则确认的只读命令自动通过。模型低风险评分与历史通配白名单都不能替代这个判定；旧白名单数据保留兼容，但不再授予未知命令自动执行权。
2. 计划执行使用独立的 `submit_change_plan` 主机工具。运行时仅启用 Bash 只读调查和该工具，不允许 Pi 写文件、MCP、子 Agent 等能力绕过计划审批。恢复即时模式时恢复原工具集合。
3. 计划是 Main 深拷贝并摘要绑定的不可变快照。审批绑定窗口、运行、会话、终端实例、连接身份与十分钟有效期。终端关闭、连接身份/就绪状态变化、取消和运行结束都会撤销授权；即使随后重新连接同一主机也不能复活旧授权。
4. 备份不是泛化的模型声明。首版文件备份必须使用明确绝对路径、`install -m 600`，不得覆盖已有备份或符号链接；独立检查可读普通文件、源/备份逐字节一致及预先批准的 SHA-256。在每次变更或恢复前再次核对备份摘要。
5. 自动变更限定为明确目标文件的 `cp --` / `install -m 600 --`、明确 `.service` 的启停/重启/重载，以及指定 context/namespace/单资源、带 `--current-replicas` 原子前置条件的 Kubernetes 副本调整。暂不自动执行任意脚本、SSH 命令包装、删除、主机重启、通用 apply/patch、数据库迁移等操作。执行 SSH 目标上的计划应先选择已建立连接的终端。
6. 文件变更必须有目标文件备份；服务操作和副本调整需要明确替代保护、影响、停止条件和只读验证，由操作员核验。保护不符合主机规则时，即使用户点击批准也不能执行。
7. 恢复动作默认不授权，需要在计划审批中另行勾选。仅在明确的普通步骤失败时按对应触发器执行；超时、连接变化、前置条件失败、取消、过期或无法确认退出状态时绝不自动恢复。
8. 输出成功标准采用退出码零及精确的去首尾空白输出匹配；无法确定即停止。任何计划命令都不走子终端关闭后的自动转移/重试。审核与执行记录继续可见，计划结果不向模型或命令日志回传原始命令输出。
9. 执行模式单独保存在会话字段中，旧会话默认即时执行。批准仅存内存，不写入数据库；恢复会话或重启应用不会恢复授权。原四种工作风格保持不变。

10. Electron 实测发现并修复了原终端脚本包装器的长行限制：Base64 载荷改成单份、分行的 Shell 复合块，避免备份预检等长命令超过 PTY 行缓冲而无法开始。
